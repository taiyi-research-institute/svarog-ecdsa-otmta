# 2/3 门限、批量 20 的签名性能

比较 main 0.2.0（983f041）与 sign-heavy 0.4.0（8d9a7bb）。
三方生成密钥，由参与方 1 和 3 签名；每次 sign_batch 返回 20 个签名。
sign-heavy 同时包含论文补丁和签名期 OT Setup，因此差距不能仅归因于 Setup。

| 分支 | 中位数／毫秒 | 均值／毫秒 | P95／毫秒 | 每笔摊销／毫秒 | 通信轮数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| main | 70.77 | 71.20 | 74.43 | 3.54 | 3 |
| sign-heavy | 395.57 | 396.45 | 405.10 | 19.78 | 5 |

中位数比值为 5.59，sign-heavy 每批增加约 324.80 毫秒。
每笔摊销是批量中位数除以 20，不表示单独签一笔的延迟。
每版采集 40 批，分四组交替执行，每组预热三批再测十批。

使用相同计时器、Release 构建、离线锁定依赖，两个源码快照与构建目录互相独立。
机器为 AMD Ryzen 7 5700X，当前可用六个逻辑 CPU，Tokio 使用八个工作线程。
通信器使用内存消息和事件通知，未添加真实网络 RTT。

每批记录两个签名方中较大的完整调用耗时，包含计算、序列化及通信调度。
keygen、输入分配与 keystore 克隆不计入；sign-heavy 的 OT Setup 计入。
所有调用成功，双方签名结果一致，通信计数分别为三轮和五轮。

raw.csv 保存全部原始签名样本，keygen.csv 保存单独计量的初始化结果。
refs.json 记录完整提交，environment.json 记录环境，summary.json 记录统计值。
CSV 中 baseline 对应 main，inline 对应 sign-heavy。

reproduce.py 可在本机执行，它从仓库归档两个分支，并在临时快照中将原基准限定为 2/3、批量 20。
脚本依赖仓库现有 scripts/bench_sign_setup.py 与 src/timing_bench.rs；默认读取执行时的分支头。
复现本次结果应确保分支头与 refs.json 相同，或将脚本中的分支名替换成记录的完整提交。
